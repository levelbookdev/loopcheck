# ADR 0017 — Vendor field service reports: immutable visits with attached proof

**Status:** accepted · **Date:** 2026-07-12

## Context

Manufacturer representatives visit a project for installation verification,
startup assistance, warranty service, and training. Their signed field report
often leaves as a PDF or phone photo and then disappears into email. That loses
both a turnover record and the evidence needed when a vendor later disputes
whether its installation requirements were met.

A visit belongs to either one equipment tag or one system. A project-wide
ledger must list both shapes together, while a tag page must be able to derive
whether any manufacturer representative certified the installation. The
Warranty & Closeout module may cite a visit in `warranties.basis_note`, but a
hard relation would couple two independent modules and would not cover systems.

The signed report is strongly expected but cannot be constitutive at record
creation. A tech may be offline, an upload may fail after the visit lands, or a
vendor may promise the report later. The honest state is an immutable visit
whose missing proof is conspicuous—not a lost visit or a mutable record.

## Decision

### 1. Add an append-only `service_visits` ledger

`service_visits` stores `project`, nullable `tag` and `system` relations,
`vendor_company`, `rep_name`, `date`, `purpose`, `summary`,
`installation_certified`, `certification_note`, and a unique
`client_token` generated by the phone for idempotent offline sync. `purpose` is
one of:

- `installation_verification`
- `startup_assistance`
- `warranty_service`
- `training`
- `other`

The create rule requires exactly one subject (`tag` XOR `system`) and requires
that subject to belong to the submitted project. `project` is deliberately
denormalized, following `punch_items`, so one flat indexed query serves the
project ledger. Updates and deletes are rejected for every caller. A correction
is another visit record; the first account remains part of the turnover story.

Reads and creates stay public because this is a no-install field capture flow,
like checks and punch flags. The record contains business visit facts, not the
customer PII isolated by ADR 0011. A later authentication policy may narrow
office edits elsewhere, but it must not silently strand accountless field
capture.

### 2. The report uses polymorphic `attachments`

The vendor PDF or phone photo attaches with
`parent_collection='service_visits'` and `parent_id=<visit id>`. This reuses the
published evidence mechanism instead of adding another file field. Attachment
creation for this parent is accountless so the field flow remains usable.

The attachment is not server-required. PocketBase record rules cannot require
a child attachment, and a create-then-upload sequence can fail between calls.
The capture UI therefore holds the selected file first, creates the visit,
uploads the report immediately, and loudly marks/retries any visit whose report
is absent. Later uploads append evidence without editing the visit.

### 3. Certification is derived from the ledger

A tag displays **Manufacturer-certified installation: {date}** when any of its
visits has `installation_certified=true`. Multiple certified visits remain
visible; readers use the most recent date for the prominent line and never
store a certification status on the tag. `certification_note` records the
rep/report language that supports the flag. A warranty may reference this visit
by convention in `basis_note`; there is no cross-module foreign key.

### 4. Offline capture queues the whole intent

The browser outbox stores the visit fields and the selected report blob, then
syncs in create-then-attach order. If the visit succeeds and the attachment
does not, the outbox retains only the pending attachment operation keyed to the
new visit id. Before retrying a create after a lost response, the worker looks
up the unique `client_token`; retries never create a second visit for the same
queued intent.

## Alternatives rejected

- **A mutable vendor-service record.** Rejected: a visit report is turnover
  evidence. Corrections append; history is never rewritten.
- **A stored `manufacturer_certified` field on tags.** Rejected: it would drift
  from the visit ledger. Certification is a derived fact.
- **A direct report file on `service_visits`.** Rejected: the existing
  `attachments` collection is the evidence contract, and reports may arrive
  after the field record without mutating it.
- **A relation from visits to warranties.** Rejected: the modules remain
  independently useful, and `basis_note` already records the provenance by
  convention.
- **Vendor scheduling, service contracts, or billing.** Rejected as a different
  problem domain. LoopCheck records that a visit happened and preserves proof.

## Consequences

- The application schema gains one additive collection and no existing record
  shape changes.
- A visit without an attachment is valid but visibly incomplete evidence; the
  UI must nag rather than imply the report exists.
- Project and tag readers can query the ledger directly; certification remains
  derived and cannot drift.
- The public API gains the collection plus `service_visits` as an allowed
  attachment parent. This is additive and does not require a v1 breaking-change
  bump, while the existing contract-reconciliation warning still applies to
  post-v1 collections.
